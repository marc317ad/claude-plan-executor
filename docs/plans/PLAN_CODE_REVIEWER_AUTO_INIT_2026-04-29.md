# PLAN_CODE_REVIEWER_AUTO_INIT_2026-04-29

## Goal

Make `/implement-plan` self-initialize a project-local `.claude/agents/code-reviewer.md` on first run in a consuming repo, using the existing `plugins/plan-executor/templates/code-reviewer.md.template` and deterministic repo inspection. The generated reviewer should be useful enough to unblock cross-review without a manual setup step, while preserving the current design that `code-reviewer` is project-owned and domain-specific.

## Context

The active plugin calls `Agent(subagent_type: "code-reviewer", model: "sonnet", ...)` in Phase D.1 and Phase D.5. The plugin does not ship `code-reviewer` as a plugin agent; it ships only `templates/code-reviewer.md.template`. README currently requires each consuming repo to copy and customize `.claude/agents/code-reviewer.md` by hand.

This is brittle in new repos: the plugin can run through planning and implementation, then fail mid-run when a Claude review or D.5 third-opinion dispatch needs `code-reviewer`. A first-run initializer should move this failure to Phase 0 and, when safe, fix it automatically.

The initializer must be deterministic. It must not call an LLM to author the reviewer, because setup should be cheap, repeatable, and available before the review-agent topology is trusted.

## Why Project-Local Auto-Init

`docs/plans/analysis/2026-04-26_code_reviewer_subagent_missing.md` recommends shipping `plugins/plan-executor/agents/code-reviewer.md` as a plugin-namespaced fallback and updating Phase D call sites to `plan-executor:code-reviewer`. This plan deliberately chooses a project-local initializer instead.

Reasoning:

- `code-reviewer` is the only reviewer role whose prompt is inherently domain-specific. The template asks for project pipeline, domain traps, language traps, and local conventions; a generic plugin fallback would be available but weaker exactly where cross-review should be strongest.
- The active SKILL already dispatches bare `code-reviewer`, which resolves naturally to `.claude/agents/code-reviewer.md` in the consuming repo. Auto-init preserves that topology and removes the manual setup footgun.
- A plugin-shipped fallback remains a valid follow-up if Agent resolution proves unreliable or if a consuming repo refuses project-local generated files. It is not required for the first-run failure this plan targets.

Non-goal: this plan does not add `plugins/plan-executor/agents/code-reviewer.md` or rewrite Phase D to `plan-executor:code-reviewer`.

## Design

Add a new `plan_ops.py ensure-code-reviewer` subcommand.

Inputs:

- `--repo-root <path>` optional, default current working directory.
- `--template <path>` optional. Default resolution order: explicit flag, then `${CLAUDE_PLUGIN_ROOT}/templates/code-reviewer.md.template` when `CLAUDE_PLUGIN_ROOT` is set, then `Path(__file__).resolve().parent.parent / "templates" / "code-reviewer.md.template"`, else `template-missing`.
- `--write` required to create files; without it, dry-run validation only.
- `--json` emits a structured result.
- `--force` optional, rewrites an existing generated file only when it carries an explicit generator marker and an unchanged generator hash.

Outputs:

```json
{
  "ok": true,
  "status": "exists | created | would-create | invalid-existing | template-missing",
  "path": ".claude/agents/code-reviewer.md",
  "generated": true,
  "facts": {
    "project_name": "...",
    "project_one_liner": "...",
    "languages": ["python"],
    "test_commands": ["pytest"],
    "config_files": ["pyproject.toml"],
    "pipeline": "..."
  },
  "warnings": []
}
```

Existing file behavior:

- If `.claude/agents/code-reviewer.md` exists and frontmatter parses with `name: code-reviewer`, return `status: exists` and do not modify it.
- If it exists but has advisory drift (missing `description`, missing `model`, or a tools list that omits one of `Read`, `Grep`, `Glob`, `Bash`), return `status: exists`, `ok: true`, and include warnings. Do not block the run: project-local reviewer prompts in the wild may be deliberately customized.
- If it exists but frontmatter is missing/unparseable or `name` is not `code-reviewer`, return `status: invalid-existing`, `ok: true`, and include warnings. Do not overwrite user-authored content and do not halt Phase 0 by default. The Agent dispatch may still fail later, but the initializer must not turn a recoverable customization into a hard setup blocker.
- If it exists and carries a generator marker, allow `--force` to regenerate only when the marker hash matches the current file body. If the user edited the generated file, `--force` refuses with `status: generated-edited` and preserves bytes.

Generated file behavior:

- Create `.claude/agents/` if missing.
- Fill every placeholder in `code-reviewer.md.template`; never leave `{{...}}` tokens behind.
- Add a short generated marker comment below frontmatter with a content hash, for example:

  `<!-- Generated by plan_ops.py ensure-code-reviewer; hash: sha256:<hex>. Edit freely; remove this marker or expect --force to require an unchanged hash. -->`
- Write atomically with a tempfile in `.claude/agents/` plus `os.replace`. Two parallel first-run sessions may race; this is acceptable because both generate deterministic content from the same repo state. If the target appears between existence check and replace, re-read it and return `exists` unless `--force` was explicitly requested.

## Heuristic Fact Extraction

Implement a small deterministic helper layer in `plan_ops.py`, kept separate from `cmd_preflight`:

- `_detect_project_name(repo_root)`: prefer root directory basename; if `package.json`, `pyproject.toml`, or `Cargo.toml` has a name, use that.
- `_detect_project_one_liner(repo_root)`: prefer first useful README paragraph. Skip blank lines, markdown headings, badge/link-only lines, HTML-only lines, and lines longer than 180 chars. Search only the first 80 lines. Fall back to language/framework summary.
- `_detect_languages(repo_root)`: inspect sentinel files and extensions:
  - Python: `pyproject.toml`, `setup.py`, `pytest.ini`, `*.py`
  - JavaScript/TypeScript: `package.json`, `*.js`, `*.ts`, `*.tsx`
  - Rust: `Cargo.toml`, `*.rs`
  - Go: `go.mod`, `*.go`
  - Java/Kotlin: `pom.xml`, `build.gradle`, `*.java`, `*.kt`
- `_detect_test_commands(repo_root)`: prefer `CLAUDE.md` and common config:
  - Python: `pytest`, or `python -m pytest` if no pytest config but tests exist
  - JS/TS: `npm test` when `package.json` has a test script
  - Rust: `cargo test`
  - Go: `go test ./...`
- Multi-language handling: detect every stack, but mark one primary language for ordering. Primary language precedence is: explicit test command in `CLAUDE.md`, then root-level package/config file (`pyproject.toml`, `package.json`, `Cargo.toml`, `go.mod`), then highest count of non-test source files under common source roots. Emit `multi_language: true` and list all detected stacks in warnings when more than one stack is present.
- `_detect_language_traps(languages)`: maps language set to 2-4 concise review-risk bullets.
- `_detect_domain_traps(repo_root)`: keyword-based hints from README/CLAUDE/config/file paths, with conservative defaults:
  - finance/trading/payments: Decimal vs float, idempotency, rounding, replay safety
  - auth/security/crypto: authorization checks, secret handling, crypto misuse
  - data/ETL/ML: schema drift, batch size, nondeterminism, silent data loss
  - web/API: validation, auth middleware, request/response compatibility
  - default: persistence boundaries, concurrency, external side effects
- `_detect_conventions(repo_root)`: summarize config files, source/test directories, env/config conventions from visible files.
- `_detect_pipeline(repo_root)`: deterministic one-line pipeline:
  - Web/API: `request -> routing/middleware -> handler -> service -> persistence -> response`
  - CLI: `CLI args -> command dispatch -> core logic -> filesystem/process output`
  - Library/tooling: `public API -> core module -> adapters -> output`
  - Fallback: `entrypoint -> domain logic -> side effects -> result/report`

Keep all generated prose concise. The reviewer prompt should not exceed the current template by more than roughly 40 lines.

## Skill Integration

In Phase 0 of `SKILL.md`, run before normal `preflight`:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/plan_ops.py" ensure-code-reviewer --write --json
```

Routing:

- `created`: continue, and include a short note in the run summary that `.claude/agents/code-reviewer.md` was initialized.
- `exists`: continue silently.
- `invalid-existing`: continue with a warning; the project has a local file and the user may have intentionally customized it.
- `template-missing`: halt before acquiring the run lock, with the structured error.

Exact insertion point: after any single-file `decompose-plan` auto-promotion succeeds and logs `decompose_auto_promote`, but before `path-info` and `preflight`. This call intentionally uses bootstrap `python3`, matching the existing `decompose-plan` placement before `$PYTHON` is pinned.

When `created`, append a run-log event after `path-info` resolves the run-log path:

```json
{"event": "code_reviewer_init", "path": ".claude/agents/code-reviewer.md", "status": "created"}
```

If creation happens before run-log path binding, the orchestrator may hold the JSON result in memory and log it immediately after `path-info`.

## Tests

Add focused tests in `tests/scripts/test_plan_ops.py` or a new `test_code_reviewer_init.py`:

1. Missing `.claude/agents/code-reviewer.md` plus `--write` creates the file from the template.
2. Dry-run without `--write` returns `would-create` and does not touch disk.
3. Existing valid user-authored file returns `exists` and preserves bytes.
4. Existing invalid file returns `invalid-existing`, `ok: true`, warnings, and preserves bytes.
5. Generated file has no unresolved `{{[A-Z_]+}}` placeholder tokens.
6. Python repo fixture fills Python-specific traps and a pytest command.
7. JS/TS repo fixture fills package-name and npm test command.
8. Unknown repo fixture still produces a generic but valid reviewer.
9. `SKILL.md` Phase 0 references `ensure-code-reviewer --write --json`.
10. README documents that the plugin now auto-initializes the reviewer, while users may edit the generated file.
11. Existing generated file with a matching hash can be regenerated with `--force`.
12. Existing generated file with user edits refuses `--force` as `generated-edited` and preserves bytes.
13. Multi-language fixture emits `multi_language: true`, lists all stacks, and picks a deterministic primary language.
14. Run with `PATH` stripped of `claude`, `codex`, and `gemini` binaries still succeeds, proving the generator performs no LLM or reviewer shell-out.
15. Concurrent creation simulation is idempotent: second call sees `exists` or writes byte-identical content.

Doc changes:

- README: project-local `code-reviewer` is auto-created on first run, but users should review and customize it.
- Template README: document that `code-reviewer.md.template` is now consumed by `ensure-code-reviewer`.
- SKILL.md: Phase 0 insertion and `code_reviewer_init` summary note.

## Acceptance Criteria

- A fresh consuming repo without `.claude/agents/code-reviewer.md` can run `/implement-plan` and get a usable generated reviewer before Phase D.
- A repo with a hand-authored reviewer is never overwritten by default.
- Generated reviewer frontmatter is valid for the Claude Agent tool.
- Generated reviewer contains repo-aware values for all template placeholders.
- Failure modes are early, structured, and actionable; user-authored reviewer drift is warning-level unless the template is missing.
- The generator performs no network calls and no LLM calls.

## Rollback

Remove the `ensure-code-reviewer` subcommand, remove the Phase 0 SKILL call, and restore README wording that requires manual `.claude/agents/code-reviewer.md` setup. Generated files in consuming repos are project-owned and should not be deleted by rollback.

## Open Questions

- Should generated files be staged/committed by `/implement-plan`? Recommendation: no. Treat initialization as project setup state; surface it in the summary and leave normal git workflow to the user.
- Should `ensure-code-reviewer` also create `.claude/plan-executor.json` if absent? Recommendation: no for this plan; missing config already has a default fallback and is a separate setup concern.
- Should `model` stay `opus` from the template? Resolved: yes for now. SKILL dispatch forces `model: "sonnet"` on the Agent call, so frontmatter model is not load-bearing for Phase D.
